# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev          # API on :5000 (node server/index.js) + Vite client on :5173 (proxies /api -> :5000)
npm run dev:server   # API only; migrates the schema on boot
npm run build        # vite build -> dist/
npm run migrate      # bring the DB schema up to date, then exit (idempotent)
npm test             # every suite, in sequence
npm test monthly     # one suite, matched by name or filename substring
```

There is no linter or formatter configured.

Env is loaded from `.env.local` then `.env` (see `.env.example`). `DATABASE_URL` and `JWT_SECRET` are required at import time; `ADMIN_PASSWORD` is required only to seed the `admin` account on first migration.

## Tests hit the real database

`tests/run.mjs` starts the API itself if nothing answers `/api/health` on `$API` (default `http://localhost:5000`), and leaves an already-running server alone. Apart from `translations`, the suites are end-to-end: they drive the live API over HTTP and seed/clean rows directly through `pool` against whatever `DATABASE_URL` points at. They exist to prove things that only live in Postgres (CHECK constraints, the max-three-managers-per-sector trigger, `FOR UPDATE` locking, SQL scoping).

- Fixtures use `zz-` usernames and `ZZTEST`/`TEST` record names and clean up in `finally`. Never run suites in parallel. A suite creates every row it needs, including its project (`tests/fixtures.mjs`, `ZZ-PRJ-<operation>`) -- nothing seeds a project, so a hard-coded id is a suite that only passes on the machine somebody typed that row into.
- A killed run (e.g. piping into `head`) can leave fixtures and break the next run on duplicate usernames — see `tests/README.md` for the cleanup SQL.
- `translations.test.mjs` fails the build on: a key missing any of en/rw/fr/sw, a `t('key')` that isn't defined, a defined key that is never used, or hard-coded English in JSX (`<th>`, `placeholder=`, `label=`, `title=`, button text, etc.). When adding a new status/role/enum value that is rendered via a template key like ``t(`status.${x}`)``, also add it to `FAMILIES` in that test. It scans `src/` **and the server files in `SERVER_FILES`** (the report exports call `translate()` with keys of their own), so a key only the API uses still counts as used — add a server file there if it starts calling keys.

## Architecture

Vite + React 18 SPA (`src/`) and an Express + `pg` API (`server/`), with no ORM and no router library. `shared/businessOperations.js` is imported by both sides.

### Deployment shape

- **Local / ordinary host:** `node server/index.js` runs `initDatabase()` then listens, and also serves `dist/` when it has been built -- so one process on one port is the whole deployment (`npm run build && npm start`). Hashed files under `dist/assets` are cached for a year, everything from `public/` is not, and any GET that matched no route falls back to `index.html` so the hash router keeps working on a refresh. An unmatched `/api` path answers JSON 404 instead, so a wrong route never reaches the client as HTML. `npm run dev` is unchanged: Vite on :5173 proxying /api to :5000.
- **Local development, no external service:** Postgres 16 runs from `docker-compose.yml` on host port 5433 (`docker compose up -d`; a native install on the same port is an equivalent alternative), and `.env.local` points `DATABASE_URL` at it with `sslmode=disable`. **Supabase is gone** (storage, env entries, `supabase/schema.sql`) and should not come back; **Vercel is the production deployment** -- see the Vercel bullet below -- so `api/index.js` and `vercel.json` are live files, not leftovers. This bullet used to say Vercel had been removed too, which was true for one commit (`29d262c`) and then stopped being true at `695f0f9`, leaving the paragraph arguing with the one under it. `server/index.js` only migrates/listens when it is the process entry point, so importing the app never runs DDL.
- `pool.query` is monkey-patched to retry once on stale-connection errors. Transactions use `pool.connect()` and must roll back with `safeRollback(client)`.
- **Vercel:** `api/index.js` re-exports the Express app and `vercel.json` rewrites `/api/(.*)` to `/api/index` (Express still sees the original `req.url`); `npm run vercel-build` builds the client and then runs `server/migrate.js`, so **no DDL runs on a cold start**. The pool uses `max: 1` and `trust proxy` is on when `VERCEL` is set. Postgres comes from Neon, files from Vercel Blob.
- Evidence files go through `server/lib/storage.js`: local disk by default (`server/uploads/`, or `UPLOADS_DIR` for a mounted disk), or **Vercel Blob** when `BLOB_READ_WRITE_TOKEN` is set -- the routes never know which. Blob objects sit at random addresses the app never hands out, but they are not themselves permission-checked, unlike a file on disk. Uploads are capped at `MAX_EVIDENCE_BYTES` (4 MB, mirrored by `MAX_BYTES` in `journey.jsx`) because a serverless request body cannot exceed 4.5 MB. Whichever store is used must be backed up with the database. Files are only ever served through permission-checked API routes. `?token=` is accepted **only** on `GET .../evidence/:id/file`, and only a *file token* (5 minutes, bound to that one path) minted by `POST /api/auth/file-link` -- never the session token. The client's `openFile(path)` (in `useApi`) asks for one on click. Upload routes authorize the record before multer buffers the body.
- A local Postgres without TLS works by adding `?sslmode=disable` to `DATABASE_URL` (or `DATABASE_SSL=false`).
- Input validation helpers live in `server/lib/http.js` (`parseId`, strict `isValidDate`, `validNumber` with a NUMERIC-safe ceiling, `contentDisposition`). The global error handler in `server/index.js` maps bad JSON and Postgres input errors (`22P02`, `22007`, `23505`, ...) to 400/409. Route-level error handlers should `next(error)` rather than answer 500 themselves.

### Schema and migrations

There are no migration files. `server/db/database.js#initDatabase` creates the base tables, then calls `migrateMovementModule`, `migrateActivityModule`, `migrateMonthlyModule` (in that order — monthly depends on activities). Every statement must stay idempotent (`IF NOT EXISTS`, drop-then-add constraints, idempotent `UPDATE`s), and legacy status values are remapped before CHECK constraints are added. Status/enum lists are exported from the `*Schema.js` files and reused by routes.
### Roles and authorization

Roles: `super-admin` (the "Director", shown on the chart as the Super Manager), `general-manager`, `manager` (a project manager, scoped to one `sector`), `staff` (a team member), `partner` (external, view-only, one or more operations granted in `partner_operations`). `isAdmin(user)` ⇔ `super-admin`.

- **The General Manager sees everything internal and decides nothing the Director decides.** `hasFullScope` includes them (visibility), `isAdmin` does not (authority): no assigning or approving activities/trips, no projects, People, Partners, partner messages or report export. Write gates that used `hasFullScope` as permission to *act* use `actsAcrossOperations` (`isAdmin || coversAllSectors`) instead -- check this whenever a new route keys an action on `hasFullScope`. Their own authority is teams, and standing in for a project manager on the check of a team member's finished work. Created only by the Director (`POST /api/users`, `role: 'general-manager'`); no route changes an existing account's role.
- **The organisation** (`server/db/organizationSchema.js`, `server/lib/organization.js`, route `/api/organization`, screen `src/Organization.jsx`). **The organisation is not a page**: there is no Organization nav entry. `TeamsSection` sits on the Director's Projects page and on everyone else's Home (a team member sees their own team and who they report to); `OrganizationSection` (the chart, where the Director sets a project manager's line, and `organization_history`) sits on People and on the General Manager's Home. Reporting lines are `users.manager_id`, constrained by `REPORTS_TO` (staff→manager, manager→manager|general-manager, general-manager→super-admin, partner→nobody) **and** the `users_reporting_line` trigger, which also refuses loops. `teams` belong to one project (`supervisor_id` NULL = the project's manager leads it); `team_members` are `staff` only (trigger-enforced) with at most one `is_leader`. A team is created by senior management or the project's manager; members are managed by those or the team's supervisor (`canManageTeam`, sent to the client as `team.canManage`); only senior management changes a supervisor. Every change is a row in `organization_history`.
- **A team member on a live team is narrowed to their teams' projects** by `projectScope` (plus rows assigned to them -- pass `{ assignedColumn: 'a.assigned_to' }` on activity queries), exactly as a manager with projects is; a team member on no team keeps the operation-wide view.
- **A team member's finished work is checked by their project manager before the Director.** `POST /:id/completion` from a `staff` account names a checker (`checkerFor`: their reports-to manager, else their team's lead on that project, else the project's manager) in `activities.completion_checker_id` and tells them (`work_to_check`), not the Director. `POST /:id/check` (`accept: true` passes it on and notifies the Directors with `work_submitted`; `false` returns it as Needs Correction with a `MIN_CORRECTION_NOTE` reason) is the checker's, or the General Manager's standing in. `FINAL_CHECK_SQL` excludes work still waiting (`MANAGER_CHECK_SQL`), so the two queues never overlap; a manager's own hand-in has no checker and goes straight to the Director as before. Only the Director ever sets Completed, and may still do so before the check. A manager has no work register, so `#/activities/:id` alone is let through for them (`recordOnly` in `InternalWorkspace`) and shows just the record.
- **Partners by project.** `partner_projects` narrows an operation grant: once any project in an operation is shared with a partner, that operation shows them only the shared projects (`partnerProjectSql`, used by every query in `partner.js` and the counts in `partners.js`). Sharing is refused outside the partner's operations, and dropping an operation drops its project shares. Partners also have `organization` and `partner_contact_id`, and may read `/api/notifications` (their own rows only) for `partner_shared`.
- **A shared project is read in full, and exported.** `GET /api/partner/projects`, `/projects/:id/report` and `/projects/:id/report/export` (`server/routes/partner.js`) give a partner the Director's own report -- `buildReport` for that one project, so the monthly plans filed under it, objectives, every recorded day and the money -- and the same PDF/Excel through `sendReportFile` (exported from `reports.js`, shared with the Director's export). "Their project" is a `partner_projects` row only: unlike the activity lists, it never falls back to every project in a granted operation, and the project must still be in one of `req.user.operations` (404 otherwise, so ids cannot be probed). Still read-only. The portal's "My projects" tab renders `ReportBody`, handed from `App.jsx` to `PartnerPortal` as the `ReportView` prop rather than imported, so the partner's screen is the Director's screen. `tests/partner-projects.test.mjs`.
- **A shared project has its documents and a discussion.** `/api/partner/projects/:id/files` lists, and `/files/:source/:fileId` streams with the partner's own session, the evidence of the project's recorded days (`plan_report_evidence`) and activities (`activity_evidence`); a file is found by its id AND the project (`DOCUMENT_SOURCES` in `partner.js`). `/projects/:id/discussion` is the project's discussion: `partner_comments` rows with `project_id` set, about the project, one of its plans (`subject_type = 'plan'`) or one of its activities, checked to belong to the project. **A partner reads, and may reply in, the threads they opened and those opened by a partner of their own organisation** (`partnerSeesThreadSql`: `users.organization`, case and spaces ignored; a blank organisation shares with nobody), so two organisations on one project never read each other; a partner writing re-opens an answered thread. Inside, `/api/project-discussions` (`server/routes/projectDiscussions.js`) is read by the Director, the General Manager and managers in scope (`managerScope` + `projectScope` on the project), and answered and marked answered (`resolved_*`) by the Director and those managers -- not the General Manager. A partner's comment notifies the project's manager (`project_comment`; else every manager of its operation) and the Directors (`partner_comment`); an answer notifies the partners who wrote in that thread and still have the share (`partner_reply`). `loadThreads` keeps the two kinds apart: `project_id IS NULL` threads are the private messages to the Director below, and neither door answers the other's threads. `tests/project-discussion.test.mjs`.

- `server/lib/auth.js#authMiddleware` re-reads the user row on every request (role, sector, `status`, `password_changed_at`, `must_change_password`) rather than trusting JWT claims, so suspension, reassignment and password resets take effect immediately. Tokens carry only `id` and are verified as HS256; `JWT_SECRET` must be at least 32 characters.
- Every password somebody else set is temporary: the seeded Director, and any account the Director creates or resets, gets `must_change_password`. Until the owner uses `POST /api/auth/password` (current + new password; returns a fresh token and ends other sessions), `authMiddleware` answers everything except the session and password routes with 403 `PASSWORD_CHANGE_REQUIRED`, and the client shows `ChoosePasswordScreen`. The password policy lives in `server/lib/passwords.js` (8-72 characters, not the username); the client mirrors the minimum as `MINIMUM_PASSWORD_LENGTH` in `ui.jsx`.
- Internal accounts (manager/staff) are suspended or reactivated with `PATCH /api/users/:id/status`; a suspension is never blocked by held work, but the response reports it. Login is rate-limited per address and per username; `trust proxy` is off unless `TRUST_PROXY` is set (only behind a real reverse proxy).
- **Suspend, recover, delete permanently** (People). Suspend and Recover (`PATCH /api/users/:id/status`) are one press each, no dialog; both are `account_*` rows in `organization_history`. Delete is offered only on a suspended account and asks one confirm, nothing to type: `DELETE /api/users/:id` answers `SUSPEND_FIRST` (409) for anything else -- the two-step order is the protection against a stray click. It answers truthfully: `outcome: 'removed'` when no non-CASCADE foreign key in the catalogue points at the user and it holds no live work (the row is deleted), otherwise `'closed'` -- `status = 'deleted'`, `deleted_at/deleted_by`, an untypeable username, `password_hash = '!deleted'`, email cleared, operations and team places dropped, the name kept so its records still say who did the work. Refused only for your own account (`SELF_DELETE`), the last active Director (`LAST_DIRECTOR`; a Director cannot be suspended anyway) and an open till (`OPEN_TILL`: close it first). **Live work never blocks a delete and asks nobody**: open months, unfinished work, decisions and checks waiting on them, people reporting to them, teams and projects they lead stay where they are (`waitingWork` in the answer; nothing is shown on screen -- the old "Work waiting for a replacement" alert was removed at the Director's request) until `POST /api/users` creates an account of the same role working in every operation that work is in: `takeOverWaitingWork` then hands it the open work of EVERY former person in that role -- suspended or deleted -- in the same transaction via `handOver()`. Nothing is copied or reset: the plans keep their targets, progress, budgets and history and only `manager_id` changes, so there is never a second plan for a month (months re-stamped as assigned by the Director, team places incl. leadership, partner contacts), answers `tookOver` and notifies them (`work_handed_over`). `DELETE` still accepts an explicit `successorId` (`SUCCESSOR_INVALID` for the wrong role, operation or a suspended account). A deleted account is left out of the register, `/api/managers`, `/api/people`, the chart and the three-managers-per-operation count, and cannot be recovered. Partners are closed from their own register (Revoke), not here.
- **The three-managers-per-operation rule fires only when a manager can be added**: `manager_sector_limit` is `BEFORE INSERT OR UPDATE OF role, sector`, and both definitions of `enforce_manager_sector_limit` skip `status = 'deleted'`. It used to fire on every update, so in an operation already over the limit (data from before the rule) no manager there could be suspended, given a password or deleted. Every delete outcome is shown in a `dialog.notice` box, not only in the top banner.
- **A partner is invited by email and chooses their own password.** `POST /api/partners` no longer needs a password: the account gets the hash of random bytes nobody sees, and `sendInvitation` (`server/lib/invitations.js`) writes an `account_invitations` row -- only the token's SHA-256, `INVITATION_DAYS` (7) to live, one unused row per account -- and emails `#/invite/<token>` through Resend (`server/lib/email.js`, plain HTTP, `RESEND_API_KEY` + `EMAIL_FROM` on a verified domain; `APP_URL` overrides the link's base) in the Director's language (`email.invite.*`; `lib/invitations.js` is in `SERVER_FILES`). The email goes after the commit and never fails the request: `invitationResult` says `emailed`, and when it was not (no key, refused, unreachable) carries the `link` for the Director to pass on, which the screen shows in a notice. `POST /api/partners/:id/invite` sends a fresh one (the old link dies; 409 `PARTNER_REVOKED`). `GET/POST /api/auth/invitation/:token` sit outside authMiddleware under `addressLimiter`: the GET names the partner, the POST takes a policy password under `FOR UPDATE`, marks the row used and answers a session; unknown, used, expired, malformed and suspended all answer the same 410 `INVITATION_INVALID`. `AcceptInvitationScreen` in `App.jsx` is drawn for any `#/invite/` address, signed in or not. A password typed by the Director is still accepted, as before. `tests/partner-invitation.test.mjs`.
- Partners are restricted by an **allowlist** of paths in `authMiddleware` (`/api/partner/*`, `/api/notifications`, `/api/auth/session`, `/api/auth/password`, `/api/sectors`, `/api/health`). New routes are unreachable to partners by default (`/api/partner-comments` is outside it on purpose: the allowlist needs `/api/partner/` with the slash). A partner's operations are the rows in `partner_operations`, read into `req.user.operations` by `authMiddleware` on every request (`users.sector` is kept as the first of them, so `users_partner_needs_operation` still holds). `server/routes/partner.js` scopes every query to those grants, never to request params -- `?operation=` may only narrow to one of them and is refused otherwise -- and returns only `approval_status = 'approved'` + `externally_visible` records.
- **A partner's only writes are a comment to the Director and the discussion of a project shared with them** (above). The private message to the Director (`POST /api/partner/comments`, replies under `/:id/replies`), into `partner_comments` -- its own table, so no internal note can reach a partner through it and no manager route reads it. Only on an operation they hold, or a record the visibility clauses let them see (404 otherwise, so it cannot probe). Rate-limited in SQL (20/hour) because the in-memory limiter is per instance. It notifies every Director (`partner_comment`). The Director reads and answers at `/api/partner-comments`, checked with `isAdmin` -- not `hasFullScope`, so an all-operations manager cannot read it.
- Sector scoping for non-admins is done in SQL via `managerScope(user, column, values, filters)` from `server/lib/http.js`; queries build a `values` array and `$n` placeholders incrementally. Authorize against the row's current sector, not the one in the request body.
- **`projectScope(user, column, values, filters)` narrows a manager to the projects they are responsible for** (`projects.manager_id`), and runs alongside `managerScope` on the activity register, `loadActivity`, the project list and the reports. A manager responsible for NO project keeps the operation-wide view -- that is somebody covering an operation in general, and an empty project list would show them nothing. Sector scoping alone equals "their project" only while an operation has exactly one project; add a second and, without this, every manager in that operation reads the other's work, budgets and spending. `withinProjectScope(pool, user, projectId)` is the single-row form.
- Approval routing (`server/lib/approvals.js`): every activity and movement stores `approval_required_from` (a user id) + `approval_required_role` (`manager`|`director`) and a separate `approval_status` (`pending`|`approved`|`rejected`) distinct from the workflow `status`. `canApprove` (JS) and `pendingForMeSql` (SQL) are the single definition used by approve/reject endpoints, the "What I Need to Approve" queue, and the sidebar badge count in `/api/summary` — keep them in step.
- Workflow transitions are governed by a `STATUS_FLOW` map in each route module (`activities.js`, `movements.js`), mirrored on the client (`ActivityReview.jsx`, `MovementModule.jsx`). Status writes use `WHERE status = <previous>` and check `rowCount` (answering 409), so concurrent moves cannot both land. Material changes are appended to `activity_history` / `movement_history` / plan-level audit tables.
- `On Hold` keeps the record's approval state as it was, and `NOT_AWAITING_STATUSES` (Draft, Cancelled, On Hold) keeps parked work out of every approval queue.
- Closed monthly plans are read-only everywhere: `assertPlanOpen(row)` in `activities.js` guards every write to an activity in a closed plan, and `ActivityReview.jsx` hides those actions (`monthOpen`). Reopening a closed month hands its report back as `Returned`. Work in a month still in Draft cannot be started or spent against.
- Dead ends the audit found are closed, and `tests/workflow-fixes.test.mjs` keeps them closed: Rejected/Cancelled activities reopen to Pending Approval (never Draft); work that never needed approval (`allowedNextStatuses`) reopens as Approved instead; reopening Completed work clears `completion_submitted_at`; a manager's own request is assigned to them, and `canRecordExpense` follows the same "who carries it" rule as start/hand-back; activities with expenses cannot be deleted, and deleting planned work in a Confirmed month lowers the allocation with a plan-history entry; movements let their author withdraw (Pending -> Draft) and reopen refused ones (Rejected -> Draft), take figures only when Approved or later, and cannot be deleted once money is recorded. Edits, draft submission and hand-back write with `WHERE status = <previous>` + rowCount 409 like the other transitions.
- **Sending work back must say what to fix.** `Needs Correction` through `/decision` or `/status` needs a note of at least `MIN_CORRECTION_NOTE` (10) characters written for that return -- the record's standing `admin_note` never counts, and the send-back dialog enforces the same floor (`minLength`). `/status` writes the note to `admin_note`/`reviewed_by` and sends `work_returned` exactly as `/decision` does.
- **A manager's record is locked to them once it has gone to the Director** (`canEditRequest` / `MANAGER_EDITABLE_STATUSES`, mirrored by `canManagerEdit` in `ActivityReview.jsx`): `PUT /api/activities/:id` takes their own Draft, or work the Director sent back (`Needs Correction`, which the assignee may edit too) or refused. `Pending Approval` is no longer editable. A correction cannot move the requested budget or the project, and is logged as `Correction made`.
- **An activity's operation is its project's.** Create and edit refuse a `sector` that differs from the project's (`projectSector`), and a planned activity's named project must belong to the plan's operation.
- Only a `manager` (or the Director) adds activities or movements and raises approval requests; `POST /api/activities` and movement `canCreate` refuse `staff`, who follow their operation's work read-only. While a record's decision is open (`decisionOpen` in `approvals.js`, mirrored by `decisionIsOpen` in `ActivityReview.jsx`), it is approved or rejected **only** through `/approval`: the Director's `/decision` route may just put it On Hold or cancel it (409 `DECISION_PENDING` otherwise), and movement `/status` refuses Approved/Rejected. Rejecting or cancelling a movement requires a reason; every reject button asks for it in a dialog. A manager cannot be moved to another sector while holding open work there.

### The Boutique Management System (Project 5)

A fifth business operation, `boutique` (`RETAIL_OPERATION`, `kind: 'retail'` in `shared/businessOperations.js`), and one seeded `projects` row, `PRJ-BOUTIQUE` (`BOUTIQUE_PROJECT_ID`, `workspace = 'boutique'`, category "Business Operations"), which the Director's Projects page opens into the shop at `#/boutique/<tab>` with an "Open boutique" button. The four original operations and their data are untouched: `isPrimaryOperation`/`isSupportOperation` are both false for the boutique, so nothing that reasons about producing or supporting includes it, and a project with a `workspace` cannot be deleted (`PROJECT_ANCHORED`).

- **Files.** `shared/boutique.js` (every list that is both a CHECK constraint and a form's options, plus the integer-minor-unit money helpers `toMinor`/`fromMinor`/`lineTotals`/`saleTotals`, read by the till on screen and by the API), `server/db/boutiqueSchema.js` (`migrateBoutiqueModule`, called last in `initDatabase`; twenty `boutique_*` tables, all idempotent), `server/lib/boutique.js` (who may do what, `moveStock`, `audit`, `sessionFigures`, `financeFigures`, `SUPPLIER_BALANCE_SQL`), `server/routes/boutique.js` (`/api/boutique/*`), `src/Boutique.jsx` (the workspace), `tests/boutique.test.mjs`.
- **Who.** `boutiqueRole(user)` in `server/lib/boutique.js`, from the account row, never the browser: `director` (super-admin: everything, every approval, the till's payment methods, voids at once), `reader` (the General Manager: reads everything, writes nothing), `manager` (a `manager` whose operations include the boutique, or who covers every operation: runs the shop and *asks* for the sensitive things), `cashier` (`staff` placed in the boutique operation: sells, takes returns, opens and closes their own till, reads the catalogue and the stock). `boutiqueAccess` refuses everybody else before any handler; partners never reach it (allowlist). The gates are `requireSell` / `requireManage` / `requireDecide`, by action, not role name.
- **Money is RWF**, `NUMERIC(18,2)` like every money column, summed as integer hundredths. The platform records it and never moves it: a "payment" is the cashier's note of how the customer paid; a "supplier payment" is a note that the shop paid. No wallet, gateway or transfer concept anywhere (the suite checks the schema for one).
- **Stock moves only through `moveStock()`**, under `FOR UPDATE` on the variant, refusing a negative balance (`INSUFFICIENT_STOCK`, 409), writing the new figure and the `boutique_stock_movements` ledger row in the same transaction -- so `SUM(ledger) = stock_quantity` always. Sales, receipts, returns, voids, write-offs, counts and transfers all go through it.
- **Nothing is deleted.** A completed sale is undone by a **void** with a reason (≥10 chars): the Director voids at once; the manager's request puts the sale in `void_requested` and tells every Director (`boutique_approval_requested`); the Director's `/void-decision` voids it (goods back through `moveStock`, kind `void`) or returns it to `completed` with a note, and tells the requester (`boutique_approval_decided`, with `outcome`). A sale with returns against it cannot be voided. An expense is voided by the Director with a reason. Products and suppliers are archived, never removed. Every write is a row in `boutique_audit` (`GET /api/boutique/audit`, the History tab).
- **The manager asks, the Director decides** anything that changes the inventory's value with nothing sold: `boutique_stock_adjustments` (`damaged`, `missing`, `count`, `supplier_return`, `transfer_out`, `transfer_in`) sit `pending` until `/decision`; the Director's own adjustments are applied and recorded as approved at once. `delta` is the signed change (for a `count`, counted − on shelf, recomputed at approval).
- **A local shop, not a fashion boutique.** `PRODUCT_CATEGORIES` (groceries, bread and snacks, drinks, dairy and eggs, fruit and vegetables, cleaning, personal care, household, stationery, other) are what forms offer; `LEGACY_PRODUCT_TYPES` (clothing, shoes, bags, accessories) stay valid so saved products are never rewritten. The add form asks for name, category, quantity in stock and price per unit; the product code is optional (`ITEM-00012` from the variant id when blank). A second active product with the same name is refused (`PRODUCT_EXISTS`, 409), never merged. `received` is the adjustment for stock that simply arrived (adds; no reason needed; still waits for the Director when the manager records it); `ADDING_ADJUSTMENTS` is the one definition of which kinds add, read by the API and the form's before/after preview. Product creation and stock adjustments take an optional `requestKey` (unique partial index): the same key again answers the first row instead of applying twice. Changing a price is `PUT /variants/:id { sellingPrice }`, audited with before/after; sale lines keep the price they were sold at.
- **Sales found by counting the shelf** (`boutique_shelf_counts` + `_lines`, `/api/boutique/shelf-counts`, the "Count the shelf" tab): for a shop that does not ring every sale up. The manager or Director types what is left; per product `sold = expected − counted`, where `expected` is the ledger's shelf figure (opening + received − adjustments − till sales), so nothing is counted twice. Today only (pieces and money fall on the same shop day); counting more than expected is refused (`COUNT_ABOVE_SHELF`: record the delivery first). Selling and buying prices are frozen on each line; the pieces leave through `moveStock` (`count_sale`), variants locked in id order. Only the Director undoes a count (`/void`, reason ≥10, kind `count_sale_void` puts the pieces back). `financeFigures` adds counted revenue to gross sales and counted cost to cost of sales (`sales.till` / `sales.counted` / `countSales`), but not to payments received. `/reports` carries `stockProfit`: per product opening, received, sold, other, closing (opening + received − sold + other = closing), revenue at frozen prices with a sale's discount shared over its lines, cost, gross profit, and stock value at the buying price.
- **Every product says what it is counted in** (`boutique_products.unit`: kg, bottles, pieces; 30 characters, blank on older products). The add form asks for it beside the starting quantity (`UNIT_SUGGESTIONS` in `Boutique.jsx`, words in `btq.unit.*`), the edit form can change it, and every quantity on the shop screens and in `stockProfit` is shown with it (`qty()`). Quantities stay whole numbers: half-kilos are counted in 500 g bags.
- **The till.** A sale needs ≥1 line, payments ≥ total (`UNDERPAID`), change only out of cash (`OVERPAID`); a cashier sells at the catalogue price and gives no discount, a manager may override the price and discount lines or the sale (audited per line; a discount is a price change by another name); split payments are several `boutique_sale_payments` rows; a method the Director switched off in `boutique_payment_methods` is refused. **Cash is only taken, or refunded, on an open till** (`NO_OPEN_TILL`, 409): cash that went into no till belonged to no reconciliation. Mobile money, card and bank need no till. Lines are locked in variant-id order and the shelf is taken from **before** the sale line is written, because the line's foreign key takes a share lock on the variant and two sales that wrote their lines first deadlocked (`40P01` is mapped to 409 by the global handler). Unit cost is frozen on each line for the books. A **return** refunds what was actually paid per piece -- the line total less the line's pro-rata share of the sale-level discount, ÷ quantity -- and the returns against a sale can never exceed its total (`OVER_RETURN`); it restocks unless `restock: false`, which only a manager may choose (keeping goods off the shelf is a write-off). A cashier takes returns only on sales they made (404 otherwise, like the read); the manager and Director on any. An **exchange** is a return plus a new sale paid first by `'Exchange credit'` (`EXCHANGE_CREDIT`, never offered on its own, never counted as money received), its own payments covering only the rest, the leftover value refunded; **the new half of an exchange cannot be voided** (it is undone by a return), or the credit the customer used would be owed to nobody. A sale attaches to the cashier's open `boutique_cash_sessions` row if they have one.
- **The Boutique Manager reports directly to the Director.** `BOUTIQUE_MANAGER_REPORTS_TO` (`organizationSchema.js`): a `manager` whose own operations include the boutique (not one covering every operation) has `users.manager_id` = the Director, set by `POST /api/users` and `PATCH /:id/assignment` whether or not a line was chosen, refused with 400 for anything else, and refused by the `users_reporting_line` trigger even by SQL; the migration backfills existing boutique managers. The chart shows the line fixed (`org.boutiqueLine`). A cashier still reports to the Boutique Manager. The manager's channel is `boutique_submissions`: `POST /submissions/report` freezes `buildReport(period)` into `snapshot` and `POST /submissions/incident` carries words; both notify every active Director (`boutique_report_submitted` / `boutique_issue_raised`), never the General Manager (who may read them). The Director's `POST /submissions/:id/decision` (`accepted`, or `returned` with ≥10 chars) records who, when and the note on the row and in `boutique_audit`, and tells the submitter (`boutique_submission_decided`, with `outcome`). A sale that takes a variant down to its reorder level sends `boutique_low_stock` to the Directors and the boutique managers once (`moveStock().ranLow`). `/api/summary` carries `boutiquePending` for the Director (adjustments + voids + submissions), which is the Boutique badge in their menu.
- **A cashier reads the shelf, not the books.** `requireNotCashier` refuses them suppliers, purchases, expenses and the adjustments queue; `forRole`/`productForRole` strip `costPrice` from every variant they are sent, and `/overview` answers `null` for the stock's value at cost and the supplier balance. The screen hides the same things; the API is the wall.
- **Closing a till** freezes `expected_cash` (float + cash taken − change − cash refunds − cash expenses paid from it − payouts + cash put in, voided sales excluded) and `expected_by_method` beside what was counted; `cash_variance` is the day's shortage or surplus and is never recomputed. One open till per person.
- **The books never count twice** (`financeFigures`): net sales = gross − returns; cost of sales = frozen unit costs sold − cost of restocked returns; gross profit = net sales − cost of sales; net profit = gross profit − active expenses; payments received by method = taken − change − refunds, exchange credit excluded; goods bought are stock, not expenses, until sold; inventory value is the shelf at cost. `GET /reports?period=daily|weekly|monthly|custom` adds sales by day, most sold, size/colour/type demand, low stock, purchases, expenses by category, returns, payment reconciliation against the closed tills, and cashier performance. A cashier reads none of this.
- **Dates** are the shop's day (`BOUTIQUE_TIMEZONE`, default `Africa/Kigali`), not the database's UTC day.
- **The suite (`npm test boutique`)** is 237 checks against the live API; fixtures are `zz-btq-*` accounts and `ZZTEST` products/suppliers, removed in `finally`.

### Farming Management

The farm's own workspace (`#/farming/<tab>`, `src/Farming.jsx`), beside -- not inside -- the Farming operation's monthly plan, which is untouched: nothing here reads or writes `monthly_plans`, `activities` or `activity_expenses`, so no cost is counted in both.

- **Files.** `shared/farming.js` (every rule, as pure functions: validators answering codes, `runningBalance`/`productDeltas`, `farmSummary`, `farmAlerts`, the lists that are both CHECK constraints and form options, and `FARM_ERROR_CODES`), `server/db/farmingSchema.js` (`migrateFarmingModule`, last in `initDatabase`; ten `farm_*` tables, idempotent, seeds Cows/Chickens/Goats by `seed_key` with ON CONFLICT DO NOTHING), `server/lib/farming.js` (`farmRole`, `farmAccess`, `farmAudit`, mappers), `server/routes/farming.js` (`/api/farming/*`), `tests/farming-logic.test.mjs` (pure, no database) and `tests/farming.test.mjs` (end to end). `FARM_OPERATION`/`worksOnFarm` in `shared/businessOperations.js`.
- **Who.** `farmRole`: `director` (everything, and the farm budget alone), `reader` (the General Manager: GETs only, enforced once in `farmAccess`), `manager` (a manager whose operations include Farming: records, approves the team's expenses, corrects, voids, keeps animal types and alert thresholds), `staff` (team members in Farming: record production, herd changes and sales, submit expenses, raise problems, correct their own records with a reason). A team member gets no money: no revenue, costs, results, budget, alerts, reports or history, and only their own expenses.
- **Animal types are data.** `farm_animal_types` + `farm_measures` (`product`: milk, eggs; `herd`: the animals). Nothing branches on a type's name. Names are unique by `normaliseName` across active and switched-off types; a type with records is switched off, never removed (`HAS_RECORDS_DEACTIVATE_INSTEAD`, and `ON DELETE RESTRICT`); a measure's kind never changes and its unit not once anything is recorded.
- **Stock and head counts are summed, never stored.** Product stock = Σ(produced − lost) − Σ sales quantity; head count = Σ herd `delta`. Every write that moves one locks the measure row and runs `runningBalance` over the measure's whole history with the change applied, so a backdated entry, a correction or a void can never strand an earlier sale (`STOCK_BELOW_ZERO`). A day is one step: within it, what came in counts before what went out, whatever order it was typed in (a morning sale typed before the evening milking is not refused). "Sold" is only ever the sales rows -- production carries no sale -- and a sale of animals writes its herd event (`sale_id`) in the same transaction; that event is undone only by voiding the sale.
- **Expenses.** A team member's is `pending` until the Farming Manager (or the Director) decides; refusing needs `FARM_CORRECTION_MIN` characters. The manager's/Director's own is approved as recorded (`recorded_and_approved` in the history). Only a pending expense is edited; an approved one is voided with a reason and entered again. `animal_type_id NULL` = shared, never allocated. Amounts are frozen to USD at the reference rate (`convertAmount`), and a correction converts at the rate frozen on the row. Duplicates (same day, amount, currency, category, scope, payee) answer 409 `POSSIBLE_DUPLICATE` until resent with `confirmDuplicate: true`; production the same day for the same measure likewise. POSTs take a `requestKey`.
- **Figures.** `farmSummary`: per animal type a DIRECT result (its revenue less its own approved costs), the farm's `operatingResultUsd` with shared costs -- never called profit. Unit cost only with exactly one producing product and direct costs, flagged `estimate` when shared costs exist. Days without a record are counted (`daysWithoutRecord`), never zero. The farm budget (`farm_budgets`, Director only, separate from the monthly plan's) is a line, not a ceiling: nothing is refused for passing it.
- **Alerts** are computed on read from recorded rows (`farmAlerts`), with thresholds in `farm_settings` (`THRESHOLD_LIMITS`), each carrying the figures that explain it; a gap in the records never counts today and is worded as a gap. Tasks are the farm's existing activities (`sector = farming`, `scheduled_for`), `priority = 'High'` being critical: there is no second task system. No notification is sent; the Farming Manager's nav badge is `farmPending` from `/api/summary`.
- **The daily report is how the farm reports.** `POST /api/farming/daily-report` takes the whole day in one form laid out like the Director's summary table -- per measure `produced`/`lost`/`sold`+`soldAmount` (products) or `counted`/`born`/`bought`/`died`+`diedReason`/`sold`+`soldAmount` (herds), then `costs[]` and an optional `problem` -- and saves it in ONE transaction through the same helpers the single forms use (`recordProduction`, `recordSale`, `recordHerd`, `recordExpense`, `recordIssue`), so it meets exactly their checks and is all-or-nothing; a refusal carries `where` (`{ line, measureId, field }`, `{ cost }` or `{ problem }`) so the form points at the box. Blank means "nothing to say", never 0. A `counted` figure is recorded first, so a herd never counted is counted by whoever is in front of it. `requestKey` (advisory lock + the audit row) makes a double tap save once. It notifies every active Director and Farming Manager once (`farm_daily_report`, never the sender) and is kept as a `farm_audit` row (`entity_type 'daily_report'`, the figures as sent and the ids of the records made), which `GET /api/farming/daily-reports` reads for the "Reports received" list (a team member sees their own). No table of its own. The single forms stay, folded under "Add or correct one record".
- **Problems** (`farm_issues`): farm-specific blockers a team member raises to the Farming Manager; `animal_welfare` is always urgent and urgent ones are visible to every farm team member. These are not the organisation-wide Issues/escalations that were removed.
- Every write is a `farm_audit` row with before/after and the reason. Refusals carry a `code` from `FARM_ERROR_CODES`, shown by the screen as `farm.err.<CODE>`.

### Domain invariants

- **Three primary operations, one support function, and the boutique**, defined in `shared/businessOperations.js` with names in all four languages. IDs (`farming`, `agriculture`, `mining`, `movement`, `boutique`) are foreign keys everywhere and must not change. The boutique is `kind: 'retail'` and is described in its own section above; everything below about producing and supporting is about the first four. **The structure is not four equal columns**: `mining`, `agriculture` and `farming` *produce* (`kind: 'primary'`, `PRIMARY_OPERATIONS`), while `movement` — **Movement & Facilitation** — is the coordination/support layer (`kind: 'support'`, `SUPPORT_OPERATION`) that handles transport, logistics and facilitation *for* the three. It is still a `sectors` row with its own manager, plan and budget, because that is what gives it a month to work; `isPrimaryOperation`/`isSupportOperation` are what tell them apart — never compare against `'movement'` by hand. Use `operationName(id, language)` for display — these names are deliberately not in `i18n.js`. Per-operation **category presets live once** in `shared/categories.js` (`CATEGORIES`, `OPERATIONS_WITH_CATEGORIES`, `categoriesForOperation`, `OTHER_CATEGORY`), read by `src/App.jsx`, `src/MonthlyPlans.jsx` and `server/data/seedData.js` — do not restate them.
- **On screen, both a business operation and a `projects` row are called a "Project"** (rw *umushinga*, fr *projet*, sw *mradi*). The Director asked on 2026-10-25 for the word "operation" to be replaced by "project" everywhere it appears; before that the operations were "Operations" (*urwego* / *secteur* / *sekta*), and earlier still the operations were "Projects" and a `projects` row a "Work package". Wording only: code, tables, keys, the `{operation}` placeholders and the operation names (Mining, Farming ...) are unchanged, and the API's `message` strings follow the screen. Where one sentence named both levels it was reworded rather than made to say "project" twice (e.g. "That project does not belong to this plan"). The app's name, "Project Operations Management System", is a name and was left.
- **Project ≠ business operation ≠ monthly plan.** A *business operation* is one of the four fixed columns; a *project* is a named undertaking inside one operation (every activity has one); a *monthly plan* is one operation's one month with the budget approved for it (unique on `sector, month`). The monthly plan is what a manager works from.
- **A month is a list of objectives, and the Director's job ends when they are typed.** The plan is agreed with the four managers in a meeting *outside* the system; the Director types that agreed list and stops. They do not create daily activities, assign days, or approve the manager's work. `plan_objectives` holds one row per commitment (`title`, optional `target_quantity` + `target_unit`, optional `weight`); `plan_daily_reports.objective_id` says which commitment a day of work counted towards. **There is no Draft and no confirmation stage** — `POST /api/monthly-plans` creates the plan already `Confirmed`, so it is the manager's from that moment (`/confirm` survives only for months written before this and 409s on a live one). `monthly_plans.target_quantity/target_unit` are the superseded single-target columns, kept and backfilled into one objective by `migrateMonthlyModule`; a plan posted in that old shape still gets exactly one objective, which is why a month with a single objective does not require `objectiveId` on a report.
- **A support objective says which operation it is for.** `plan_objectives.supports_operation` is set only on **Movement & Facilitation**'s own plan and may name only a primary operation — the route refuses it on a primary operation's plan (Mining's objectives produce, they support nothing) and refuses a support-supports-support loop. NULL means support shared across all three rather than a false choice. This is what keeps "50 transport trips" readable as *50 trips for Mining*; the month-end report rolls it up as `supportByOperation`.
- **The daily form is generated from the objective, and is only ever the question.** `server/lib/objectiveForm.js` turns one objective into the form its manager records through — `derive()` reads the objective's own words and unit (deterministic, instant, no configuration) and is stored on `plan_objectives.form_spec` the moment the objective is written; `improve()` then asks Claude (`@anthropic-ai/sdk`, `claude-opus-5-5`, structured outputs) to write it better, in the background *after* the Director's response has gone out, and `form_source` flips `derived` → `ai`. **Every failure path — no `ANTHROPIC_API_KEY`, no network, rate limit, refusal, malformed answer — leaves the derived form in place**, which is why it is stored first rather than generated on demand; the app still runs with no external service at all. Model output is never trusted: `validate()` re-checks every field against the derived form, clamps lengths, forces the step positive and holds `quickAmounts` to the target. **Nothing generated here can move a figure** — progress is still summed from `plan_daily_reports` by `objectiveProgress`, so the generator decides the wording and nothing else.
- **Progress is always calculated, never typed.** `objectiveProgress`/`planProgress` in `server/lib/monthly.js` are the single definition, read by the plan payload, `/review`, `/updates` and the reports. An objective's percent is `done/target` capped at 100; a month's overall figure is the weighted average when any objective carries a `weight`, otherwise the plain average of the countable objectives. An objective with no `target_quantity` has `percent: null` — **not 0%**: "nothing to count" and "nothing done" are different, and a month of uncountable objectives never completes itself. Reporting past an objective's remaining target is refused (`OVER_TARGET`) under a `FOR UPDATE` lock on that objective.
- **A project's completion** (`GET /api/reports/projects`, scoped like the reports) is `planProgress` over the objectives of every monthly plan filed under it (`monthly_plans.project_id`); `percent: null` with `missing` (`no_plans` / `no_objectives` / `no_countable`) when nothing can be counted. It carries no money. `projects.progress` is a typed legacy number and is not used. `GET /api/reports/trends?months=N` is `buildMonthlyWork` per month, so a trend point always equals that month's report. Both render from `src/Progress.jsx` on the Director's Home and the Reports page. An objective with no day recorded shows "No progress recorded", not 0%.
- **No approved budget means no ceiling.** `approved_budget` is optional now that a month is agreed as objectives. A stated ceiling is still enforced to the cent exactly as before; a plan with `approved_budget = 0` is treated as *unlimited* rather than as a budget of zero, which used to refuse every cost the manager recorded and told them to request a budget change.
- **The month has two levels of work, in one table.** (The older activity structure, still supported alongside objectives — most months need only objectives and daily reports.) A **planned activity** is an `activities` row with a `monthly_plan_id` and no `parent_activity_id`: what the Director set for the month, with a budget out of the month's. The manager's **day-by-day work** is a row with both, created only through `POST /api/monthly-plans/:id/activities/:activityId/work`: one row per day, with `scheduled_for`, an assignee, its own budget and its own evidence. There is no third entity. Both levels carry `monthly_plan_id`, so **every plan-level budget sum must filter `parent_activity_id IS NULL`** or each budget is counted twice; spend is summed over both levels, because that is where it lands.
- **The platform records money, it never moves it.** No payment, wallet, transfer or gateway concept anywhere (a test guards this).
- **Assigning a month is a stamped act.** `monthly_plans.assigned_by/assigned_at` are set when a manager is named (creation or `PATCH /:id`) and shown to the manager as "Assigned by". `plan_objectives.deadline` is optional per objective (NULL = month end); it feeds the `overdue` counts in `/api/summary` and `objectiveState()` in `src/Home.jsx` (not started / in progress / done / overdue, derived, never typed). A manager cannot edit targets; `POST /api/monthly-plans/:id/change-request` writes a `Change requested` history row and tells the Director.
- **Notifications are in-app only** (`server/lib/notifications.js`, table `notifications`, routes `/api/notifications`). The server stores `kind` + `params`, never a sentence; the browser renders `notice.kind.<kind>` in the reader's language (`noticeSentence` in `src/Home.jsx`, and `NOTIFICATION_KINDS` in `monthlySchema.js` must stay in step with the `notice.kind.` family in `tests/translations.test.mjs`). `notify()` is called inside the transaction of the change it announces. Events: plan assigned/changed and objectives set/changed/removed (to the manager), change requested / report submitted / work submitted (to every active Director, never the actor), report accepted/returned and work approved/returned with the reason (to the manager or assignee). **Everything else between the Director and a manager notifies the other side too**: a day recorded or corrected (`day_recorded`/`day_corrected`, to the Directors, with the objective's title), a day the Director removed (`day_removed`, to whoever recorded it, with the reason), work added to a month or handed to somebody (`work_assigned`; work that must also be accepted sends only this one), an approval asked for and answered (`approval_requested` to the approver, `approval_decided` with `outcome` to whoever asked -- activities and trips alike), a budget change asked for and answered (`budget_change_requested`/`budget_change_decided`). In activities.js and movements.js these go through `tellPerson`, which never tells the actor. `tests/notifications.test.mjs`. Notifications send no email or SMS; the one email PMS sends is a partner invitation (below). The bell lives in `AppShell`; a manager's unread plan/return/approval notices also appear as cards at the top of `Home`.
- **Plain words for statuses.** Plan `Confirmed` is shown as "Active" (the DB value is unchanged). The month-end "Submit for review" form shows for whoever `canWorkPlan` on an Active / In Progress / Completed month whose report is not Submitted or Accepted (it used to require `Confirmed`, which no worked month ever is). `POST /:id/report` uses `canWorkPlan`, the same rule as recording a day. Reopen is offered only on a Closed month. Sending work back through `PATCH /activities/:id/status` with `Needs Correction` clears `completion_submitted_at` like `/decision` does.
- **A period report is read in one order, and it names nobody** (`server/routes/reports.js`, `ReportBody` in `src/App.jsx`). What was done, then the money, then the day-by-day record, and the activity register last and only when the period has activities in it. `buildMonthlyWork` starts from **the months the period falls in** and lists **every objective agreed for them**, so an objective nobody touched prints "nothing recorded in these dates" instead of being absent -- an untouched commitment and a non-existent one used to read identically. Progress comes from `objectiveProgress`/`planProgress` in `server/lib/monthly.js`, never recomputed here, and the month’s spend is summed the way `PLAN_TOTALS` sums it, so a report cannot disagree with the plan it reports on. The month’s money and the register’s three budget figures are separate labelled blocks and must never be added together. **No report carries a person’s name** -- not who recorded a day, raised an activity, asked for a budget change or answered it, and there is no per-manager table: the people reading these reports know who runs each operation, and every name is in the record’s own history screen. The screen, the PDF and the spreadsheet all render from one payload, so a month of objectives can never read as a full report in one and an empty one in another (it did: the screen short-circuited on `activitySummary.total === 0` and threw `monthlyWork` away while the PDF printed it).
- **A day is printed the way it was typed.** `DAY_COLUMNS` in `shared/dailyReport.js` -- Date, Activity (the objective), Description (`notes`), Quantity, Cost (USD), Status, Remarks, Photos -- is the order of the manager's day form and of every place a day is shown: the plan's day table, the report screen, the spreadsheet's day sheet and the PDF's day table, all headed by the `day.*` keys. Add or move a column there, never in one renderer. `work_status` is the manager's own words, never an approval; the objective's generated wording (`objectiveForm.js`) is shown as hints and placeholders under these headers, not as headers of its own.
- **Only the Director exports or prints a report -- and a partner, for a project shared with them** (below). A manager reads reports on screen; `GET /api/reports/activities/export` answers 403 `EXPORT_DIRECTOR_ONLY` to anyone else, and `ReportBody` draws the export/print buttons only when it is given `onExport`/`onPrint`.
- **A manager corrects only their own latest day** (`PUT /api/monthly-plans/:id/reports/:reportId`): work, cost and notes, never the date or objective, while the month is open and its month-end report is not Submitted/Accepted, under the same target/budget checks as recording it (with the day's old figures taken out). The Director cannot rewrite a manager's day. A manager's Home shows only that one day (`/updates?mine=1&limit=1`, whose `correctable` mirrors the route); the Director's shows the five newest.
- **An exported report is written in its reader’s language.** `GET /api/reports/activities/export` takes `?language=` (the browser sends the language it is displaying; `knownLanguage()` falls anything else back to English) and every word in the PDF and the spreadsheet comes from `shared/strings.js` -- the same dictionary the screen reads. Month and day names come from `Intl` with that language; **money does not change** -- amounts stay grouped as `formatUsd` groups them on screen, so a figure read off the screen and the same figure read off the file are the same characters. The `export.*` family is only the words a file needs and a screen does not.
- Monthly budget math (`server/lib/monthly.js`) is done in integer cents: a spend of exactly the remaining budget is allowed, one cent over is refused with `OVER_BUDGET_MESSAGE` verbatim. Closed plans are read-only. Month values are `'YYYY-MM'` parsed by hand (not `Date`) to avoid timezone shifts; the same care applies to date-only strings on the client.
- **`monthly_plans.approved_budget` is the Director's ceiling and is never recalculated.** It is typed when the plan is created or edited; `/confirm` only refuses a plan with no budget or one already over-committed. Three figures are derived from the rows and must stay derived: *committed* (sum of the planned activities' budgets), *spent*, and *remaining*. Anything that adds to a month or raises an activity's figure — `POST /:id/activities`, `POST /:id/attach/:activityId`, the `/decision` route and approving a budget-change request — checks the ceiling with `fitsBudget` under a `FOR UPDATE` lock on the plan row and refuses with `overMonthlyBudgetMessage(remaining)` ("This activity exceeds the remaining monthly budget of $200."). The day-by-day route checks the *planned activity's* own remaining the same way (`overActivityBudgetMessage`). **Never make the allocation follow the activities** — that is the bug this replaced: adding work raised the budget to cover itself, so a month could not be over budget and the refusal could never fire. Lowering the allocation below what is committed is refused.
- **The month's money is exactly three cards** -- Approved Budget, Actual Spent, Remaining Budget (`BudgetCards` in `src/Progress.jsx`), on the plan page, the monthly overview and the Director's Home. Never add a Pending Approval or Total Planned Budget card. Remaining = Approved − Spent and is shown negative with a warning when spending passes the budget; a month with no budget reads "No limit set". Across several months (the review totals, the period report's `money`) Remaining is taken only over months with a budget and the rest is `spentWithoutBudget`. `plan_objectives.planned_amount` (USD, optional, `>= 0`) is a planning figure: never added to the approved budget, never a ceiling; RWF/CDF are shown beside it only when a rate has actually been set (`rate.id`), because `getCurrentRate` answers a built-in fallback (1450/2850) when none has.
- Money is recorded on the **day of work**, never on a planned activity that has days under it (the expense route refuses it), so the same budget cannot appear available twice. A planned activity with live work under it cannot be deleted.
- Work is assigned to a `manager` **or a `staff` member** (`/api/people` lists both, in scope; `/api/managers` still lists only managers and is what the "who runs this?" selects use). Assigning to staff sets `approval_required` false — a team member has no approval screen — and reassigning work to staff while a manager's decision is still pending is refused.
- `description` is required on every route that creates work, and `evidence_required` (default TRUE, so existing rows keep today's rule) decides whether evidence is demanded before work can be handed back.
- Movements freeze the exchange rate (`fx_rwf_per_usd`, `fx_cdf_per_usd`) onto the row; `exchange_rates` is append-only history. Currencies: RWF, USD, CDF.
- **The trips register belongs to `TRIPS_OPERATION`** (`shared/businessOperations.js`), which is `farming` — Farming & Movement. Every gate reads that constant or `runsTrips(user)`: `canCreate`, `visibilityScope`, `canEdit` and the evidence-upload check in `movements.js`, `movementVisibility` in `partner.js`, and `coversTrips`/`coversMovements` in `App.jsx`/`MovementModule.jsx`. Never re-derive it from a literal — it was six hand-written copies of `sector === 'movement'` before, and they drifted the moment the operation changed. Not to be confused with `movements.sector`, which is the literal `'movement'` on every row — a marker that the row is a trip, unrelated to who manages it. **`related_area` accepts any of the four operations, Facilitation included, or NULL** for a trip that supports no other operation; the old `movements_related_area_check` forbidding `'movement'` was dropped (it existed only while that id ran the trips), and `related_area REFERENCES sectors(id)` is what keeps the value valid. The client's `LINKABLE_AREAS` is derived from `BUSINESS_OPERATIONS`, not listed by hand.

### Frontend

- `src/App.jsx` has three layers:
  - `App` owns the session: `ops-token`/`ops-user` in localStorage, read defensively. It re-validates via `/api/auth/session` on start, and only a real 401/403 signs you out.
  - `LoginScreen` holds its own form state.
  - The workspace is `InternalWorkspace` or `PartnerWorkspace`, keyed by `user.id:token`. Signing out unmounts it, which resets all state.
- `useApi(token, onExpired)` provides `fetchJson`, `upload` (multipart) and `download` (blob).
  - A 401, or a 403 with `code: 'ACCOUNT_INACTIVE'`, ends the session.
  - Auth refusals carry a `code` (`TOKEN_INVALID`, `PASSWORD_CHANGED`, `BAD_CREDENTIALS`, ...). `authRefusal()` maps each code to translated text.
  - Other errors show the server's `message` only; request details go to the console.
- **Routing is the URL hash, with no router library.** `useHashRoute()` in `src/ui.jsx` gives addresses like `#/activities`, `#/activities/:id`, `#/activities/new` (the add form, in a sheet), `#/activities?filter=work|final-check` (what the home tiles open), `#/movements/:id`, `#/movements/new`, `#/monthly/:planId`, `#/reports`, and partner tabs like `#/overview`.
- **Navigation is per role, not one menu with buttons hidden** (`navItems` in `InternalWorkspace`): each entry is `[id, label, badge, group, shortLabel]`. A **team member** gets My work (their team is on it) and My activities; a **manager** gets Home (their teams, and the work they must check, are on it) and My plan (`monthly`) -- the Director's decision: they see their monthly plan and work on it, and Home shows their latest day with Edit (no approvals, work register, trips, reports or requests; the plan page hides its change history from them); the **General Manager** gets Home (`GeneralManagerHome`, with the teams and the chart), Monthly plan, Activities and Reports, all read-only apart from teams. There are no Issues/escalations and no Other requests pages any more: both were removed at the Director's request (their old tables are left in the database, unused). Work the Director assigns from the Activities page is sent with `approvalRequired: false`, because a manager has no page to accept it on. The API still answers a manager's scoped reads (reports included), which the scoping tests rely on; the **Director** gets every page in three groups -- `main`, `review` (Reports) and `manage` (Projects, People, Partners). When adding a page, add it to the roles whose *job* it is, not to everyone. `bottomNav` mirrors the main group; its "More" button only renders when something is actually behind it. A role reaching a URL it has no nav entry for lands on the dashboard. The **Boutique** entry (`#/boutique`, `src/Boutique.jsx`) goes to the Director and the General Manager always, and to a manager or team member only when `worksInBoutique(user)`; the boutique chip under the logo opens it too, and the Projects page's `PRJ-BOUTIQUE` row has an "Open boutique" button.
- **The manager executes the Director's planned activity, on that same row.** Pressing Work in `MonthlyPlans.jsx` opens `Workspace` inside the planned-activity card -- no route, sidebar or page change, because leaving the month to record a day's work was what made the month feel like somebody else's screen. It reads `GET /api/activities/:id` and `/expenses` (what the record screen reads) and reuses `ExpensePanel`, `EvidenceUpload` and `EvidenceList`, so there is no second work system. `PATCH /api/activities/:id/progress` writes the manager's side of the same row -- `progress`, `work_performed`, `days_worked`, `manager_note` -- and starts approved work, so typing is never lost to a separate "start" press. Nothing is created: the plan is the source of truth and this is its execution state. Finishing still goes through `POST /:id/completion` and the Director's final check; the manager cannot set Completed themselves.
- **One action per record, in one place.** `nextAction(activity, user, t)` in `journey.jsx` answers "what do I do now?" and is read by the work cards (`Home.jsx`), the planned activities (`MonthlyPlans.jsx`) and the record screen's `NextStep`, so no two screens can disagree. It returns a single step, never a menu, and every key maps to a route that re-checks permission. A planned activity with day-by-day work under it returns no action: the work, the money and the photos belong to the days, which is what the expense route enforces.
- **Home** (`src/Home.jsx`) answers "what do I need to do?": for the Director, five doors (Create monthly plan, Review work, View managers, View reports, View budgets), a "Needs your attention" list and tiles (`activePlans`, `objectivesInProgress`, `objectivesCompleted`, `overdueWork`, plus the three below) and a budget line from `plansBudget/plansSpent`; for a manager, "My {month} plan" with objective counts and one action per objective (Start / Update / Submit for review), all opening the plan. `ReviewQueue` (same file) is the Director's "Review work" list on the `approval-queue` page: submitted month-end reports and final checks. Tiles whose counts come from `/api/summary` (`myOpenWork`, `finalChecksWaiting`, `monthEndReportsWaiting`, the approval badge) built from the same SQL as the lists they open (`openWorkSql`/`FINAL_CHECK_SQL` in `server/lib/monthly.js`, `?awaiting=work|final-check` on the activity list); quick actions; decision cards (`DecisionList`, also used on the approvals page); and a card per business operation in scope with this month's `MoneyBar` from `/api/monthly-plans/review`. The open record comes from the address, so Back closes it and refresh keeps it. Callbacks passed to modules for routing must be stable (`useCallback`), because modules key their load effects on them.
- **Shared UI lives in `src/ui.jsx`:**
  - `ErrorBoundary`: one in `main.jsx`, and one per view keyed by the view.
  - `DialogProvider`/`useDialog()`: `confirm`/`prompt`/`password`. Never use `window.confirm`/`prompt`/`alert`.
  - `DetailView`: inline and scrolled into view on desktop; a full-screen sheet at ≤900px.
  - `useBusy()`: one action at a time. Handlers that must report success return `true`/`false`, so forms reset only on success.
- **Data loading.** `loadData()` in `InternalWorkspace` refreshes in the background. Only the first load shows the full spinner. Every loader numbers its requests and ignores stale responses. The activity register is paged from the server (`GET /api/activities?paged=1&limit&offset`, with filters); the dashboard queues use the newest 200. Modules call `onChanged` so the shell's badge and queues refresh.
- **Layout.**
  - ≤900px: the sidebar becomes a drawer behind `.mobile-bar`, and detail views and dialogs become sheets.
  - ≤640px: tables with class `card-table` render as cards. Give each `<td>` a `data-label={t(...)}`, the title cell `className="card-title-cell"`, and the actions cell `className="card-actions"`. Tables without `card-table` scroll horizontally.
  - Inputs are 16px on phones to avoid iOS zoom. Styling is plain CSS in `src/styles.css`.
- **Easy to use for people who read little.** The sign-in screens offer the four languages as large buttons in their own words (`LanguagePicker buttons`). Buttons that move work forward carry a picture (`ActionIcon`/`STEP_ICONS` in `ui.jsx`) and the `big-action` size. A team member's record screen is the simple view (`simple` in `ActivityReview.jsx`): three picture steps (`SimpleSteps`) instead of the five-step journey, a "Finish by" line instead of the people line, money and dates folded under "More", the expense form folded, and the uploader starting on a photo of the work. A manager's month opens with a "Write today's work" button that jumps to the day form. Keep new screens for these two roles to one obvious action, a picture on it, and plain words.
- **Record screens** (`ActivityReview.jsx`, `MovementDetail` in `MovementModule.jsx`) share the pieces in `src/journey.jsx`: `activityJourney`/`movementJourney` work out a five-step journey (plus a side state such as Refused or Paused) from the existing status, approval and hand-back fields -- no new state -- and `journeyLabel`/`journeyTone` give lists the same words. Each record reads: `Journey`, a `NextStep` box whose buttons are only drawn when the reader's permissions allow that step, a `MoneyBar` (approved / spent / left), then folding `Section`s (details, money, receipts and photos, Director tools, history). `FilePicker` offers "Take a photo" (`capture`) and "Choose files" with previews and the server's own type/size limits. A receipt can be added in the expense form itself; `recordExpense` in `App.jsx` saves the expense and then uploads the receipt linked to it.
- **i18n** — the dictionary is `shared/strings.js`, **not** `src/i18n.js`:
  - `shared/strings.js` holds every `STRINGS` entry (one key with `en`/`rw`/`fr`/`sw` on the same line), plus `translate`, `fill`, `LANGUAGES`/`LANGUAGE_CODES`, `knownLanguage` and the test helpers. It is in `shared/` because **the API reads it too** — an exported report is written in its reader's language — and it must stay free of React and of `localStorage` for that reason.
  - `src/i18n.js` is the browser's layer over it: `storedLanguage`, `setDisplayLanguage`/`displayLanguage`, `LanguageContext`, `useT`/`useI18n`/`useLanguage`. It re-exports everything from `shared/strings.js`, so client code still imports what it always did from `./i18n.js`.
  - Components use `useT()`/`useI18n()`. Non-component helpers use `displayLanguage()`/`translate()`, which is why `App` calls `setDisplayLanguage(language)` during render.
  - Audit-trail actions written by the server in English are shown through `trailActionLabel()` (`history.<Action>` keys).
  - Every user-visible string must go through a key.

## Code style

The codebase favours long explanatory comments that state *why* a rule exists (often referencing a past bug or a spec section). Match that density when changing security, money, approval or scoping logic.
